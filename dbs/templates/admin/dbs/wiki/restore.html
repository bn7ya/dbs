Restoring

Rehearse first

Dry run performs the real load inside a transaction it rolls back, and writes no files. It reports what would be restored and changes nothing.

Merge or replace

By default a restore merges into existing rows. Replace instead of merge clears the backed-up models first — children before parents, in the same transaction as the load — so a failure leaves the database untouched.

When this project differs from the backup

A restore compares the backup with this project before it writes anything, and a dry run reports the same. It refuses a backup holding models this project does not have, naming them with their rows and files; Allow missing models restores everything else and leaves those out. A backed-up model with no table stops the restore until migrate runs. Every other difference is restored and listed as a warning:

  • a field in the backup that this project's model lacks: its values are left out;
  • a field this project has that the backup lacks: new rows get its default, rows already here keep their value;
  • a file whose field this project lacks: it is left out;
  • migrations applied on one side only, each named, and another Django version.

When the database refuses a row

The load is one transaction. A row the database refuses, a value that does not fit its field, or a foreign key that does not hold stops the restore with the model, the row and the reason, and nothing is changed. Where every file goes is checked before the first row is written; if writing a file still fails, the message says how many were written.

Permissions and content types

Every server recreates its permissions and content types when it migrates, numbered in the order it migrated, so a backup refers to them by name rather than by number: a group's permissions, a user's permissions and a generic relation all land on the right rows of a server migrated in another order. A permission the server no longer has is left out with a warning; a foreign key it cannot find stops the restore and names the row.
